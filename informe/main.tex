\section{Resumen}
Se construyó una canalización completa para generar SQL de lectura a partir de un esquema y una pregunta en español. La base experimental contiene 2,592 pares aceptados sobre 12 esquemas de entrenamiento y 40 preguntas sobre dos esquemas inéditos. Todas las consultas de referencia se ejecutaron sin error en MySQL 8.4.10 con \code{ONLY\_FULL\_GROUP\_BY}. El repositorio implementa dos configuraciones QLoRA que difieren únicamente en el rango, evaluación por ejecución y una reparación opcional. Al momento de congelar este borrador, las corridas en GPU T4 aún no se habían realizado; por integridad académica, sus métricas se reservan explícitamente.

\section{Problema y contrato}
La función oficial \code{generar\_sql(esquema, pregunta, ejecutar=None)} devuelve una sola sentencia \code{SELECT} o \code{WITH ... SELECT}. No emplea APIs externas, no ejecuta operaciones mutables y usa generación determinista. \code{config.json} permite activar o desactivar el adapter sin cambiar el prompt. El callback \code{ejecutar} se usa como máximo dos veces: una prueba inicial y, solo si falla, una reparación guiada por el mensaje del motor.

La aplicación React y la API FastAPI son una capa de demostración y no forman parte de la ruta evaluada. La salida pasa por una guardia basada en análisis sintáctico que rechaza sentencias múltiples, DDL y DML.

\section{Datos}
\subsection{Construcción y procedencia}
Se diseñaron 14 esquemas relacionales sintéticos y revisables, cada uno con cinco tablas, claves foráneas, índices y datos semilla. Doce dominios se asignaron a entrenamiento; \emph{aerolínea} y \emph{eventos} se congelaron para validación. Las plantillas cubren filtros, orden, agregaciones, agrupación, \code{JOIN}, subconsultas y ventanas. La semilla global es 2026 y cada fila registra fuente, licencia, dificultad y esquema.

\section{Metodología experimental}
\subsection{Modelo, cuantización y prompt}
Se usa \code{Qwen/Qwen2.5-Coder-1.5B-Instruct} en cuantización NF4 de 4 bits, cómputo FP16 y checkpointing de gradientes. El prompt incluye el dialecto, el esquema, la pregunta y la restricción de emitir únicamente SQL. El mismo texto se usa para baseline y adapters.

\subsection{Comparación controlada}
\begin{table}[H]\centering\caption{Única variable experimental.}
\begin{tabularx}{\textwidth}{@{}lccXX@{}}\toprule Corrida&$r$&$\alpha$&Constantes&Hipótesis\\\midrule A&16&32&dropout .05, semilla 2026, datos y épocas&Menor costo, capacidad suficiente\\B&32&32&dropout .05, semilla 2026, datos y épocas&Mayor capacidad para composición compleja\\\bottomrule\end{tabularx}\end{table}
El entrenamiento separa desarrollo por esquema, guarda métricas y tokenizer junto con cada adapter y exige un smoke test antes de la corrida completa. La selección final no usa loss: gana la mayor exactitud de ejecución ponderada.

\subsection{Métrica y experimento de reparación}
La exactitud por ejecución (EX) compara resultados normalizados: redondeo numérico a dos decimales, columnas adicionales permitidas y orden exigido solo cuando el caso lo indica. Los pesos son 1, 2 y 3 para dificultad fácil, media y difícil. Para el adapter ganador se comparará generación directa contra una única reparación tras un error de MySQL.

\section{Reproducibilidad y riesgos}
El entorno SQL se fija mediante Docker en MySQL 8.4.10. Los tres notebooks recorren datos, entrenamiento y evaluación en orden. Diecisiete pruebas locales cubren configuración, seguridad SQL, normalización de resultados, contrato oficial, API y dataset. El principal riesgo restante es el cambio de dominio entre esquemas sintéticos y evaluación oculta; se mitigará reportando EX por dificultad y una predicción conservadora, nunca sustituyendo datos faltantes por estimaciones presentadas como mediciones.

\section{Conclusiones}
La infraestructura, los datos y la evaluación están listos y verificados. El proyecto separa con claridad lo medido de lo todavía pendiente. Las conclusiones sobre el efecto del fine-tuning, el rango ganador y la utilidad de la reparación solo podrán escribirse después de las corridas T4. Esta decisión mantiene trazabilidad y evita sobreinterpretar resultados inexistentes.
